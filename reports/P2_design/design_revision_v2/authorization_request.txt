## 5. Mandatory finding-by-finding revisions

### V2-F01 — CRITICAL: D07/D08 diagnostic coverage

The previous M1 diagnostic fixes the B2 ready-task order, takes at most four currently ready tasks, minimizes the mean predicted finish of H tasks in that prefix, and constrains each local L finish to be no later than its local baseline finish.

The audit demonstrated that this diagnostic can report zero opportunity when a currently selected L task blocks a later H successor on a scarce resource. Changing only the FINE/COARSE threshold does not repair this observation blind spot.

Required work:

1. Preserve the v1 M1 definition as a separately identified historical diagnostic.
2. Specify its valid interpretation and explicit negative-result limitation.
3. Propose a revised, bounded diagnostic that can examine a remaining H dependency path within the already-arrived public DAG and the approved public estimates.
4. State exactly which arrived nodes, completed predecessors, ready tasks, visible running tasks and resource states are observable.
5. Explicitly prohibit future arrivals, private true durations, hidden event queues, unobserved execution truth and any feedback from the diagnostic into the actual scheduler.
6. Define the diagnostic's baseline, admissible alternative assignments, local L constraints, objective, deterministic ties, maximum search size, truncation behavior, record schema and independent recomputation.
7. State how the revised diagnostic distinguishes:
   - no opportunity within the tested local action space;
   - no opportunity observed because coverage is insufficient;
   - an invalid or incomplete diagnostic.
8. Explain what a negative result does and does not imply about the registered remaining-H-path mechanism.
9. Compare the revised diagnostic with v1 and identify the new scientific assumptions it introduces.

Do not automatically replace M1 with an unrestricted optimal scheduler or a new online candidate.

Do not assume a mathematically plausible diagnostic is already scientifically validated.

D08 must be revised consistently with the chosen proposed observation definition. Keep every proposed cutoff, coverage requirement and aggregation rule explicit and UNAPPROVED.

### V2-F02 — CRITICAL: First-materialization identity cycle

The v1 design creates a dependency cycle between workload content hash, run identity, identity locking and initial materialization.

Design an acyclic, auditable lifecycle separating at least:

1. Approved immutable workload blueprint and generation authorization.
2. A pre-materialization lock based only on already-known identity fields.
3. Workload materialization and a generation receipt.
4. An independently verifiable input-resolution receipt.
5. Resolved workload content identity and actual workload ID.
6. Run and attempt identity.
7. A pre-invocation guard.
8. Actual process execution and raw-output preservation.
9. Independent validation, metric derivation and deterministic replay.
10. Atomic completion publication.

Define the exact identity dependencies, required fields, hash preimages and state transitions.

No hash preimage may depend on its own future hash or a future run ID.

The immutable blueprint hash must not be retroactively changed by filling fields that are only known after materialization.

Explain idempotent recovery after each interruption point without overwriting failed or incomplete evidence.

Do not implement the lifecycle in code.

### V2-F03 — MAJOR: Exact keyed-generation and identity specification

Replace conceptual field lists with an explicit typed schema.

Specify:

- Root schema version and generator version, including their exact correspondence.
- Field names, types, nullability, ordering and canonical encoding.
- Exact key material for every stochastic field, including arrival jitter.
- The treatment of scenario, condition, configuration, service slot, node, resource, edge, field and counter domains.
- Which fields are deliberately excluded from perturbation keys.
- The distinction between parent input identity and H_ISOLATED/LOW_COMPETITION control identity.
- Exact JSON canonicalization, Unicode/ASCII rules, numeric representation, duplicate-key rejection and hash scope.
- Separate semantic hashes and raw-byte hashes.
- Exact preimage objects for blueprint, materialized input, generation receipt, resolved input, run and attempt identities.
- The handling of H-only control interval G, explicitly identifying the service set over which it is computed.
- The exact conversion from keyed digest to numeric perturbation and then to the runtime representation.

Add static golden byte vectors using synthetic, non-scientific fixture identifiers. Record expected canonical bytes and hashes so two independent implementations can compare results.

These vectors must not use reserved scientific outcomes or generate calibration realizations.

Do not invent an unregistered random source or rely on mutable PRNG state.

### V2-F04 — MEDIUM: Public-view identity and denominator deduplication

Separate decision-event identity from state-equivalence identity.

Specify:

- A canonical public snapshot schema.
- The exact fields included and excluded from the state-equivalence key.
- The deduplication scope: per run, per trial, or another explicitly justified scope.
- Treatment of decision sequence numbers and repeated digests.
- Empty dispatch calls.
- Same-time events that genuinely change state.
- Post-completion refreshes.
- Snapshot references used by deterministic replay.
- Whether repeated snapshots are excluded from the M1 denominator and how this is independently checked.
- How missing snapshot data differs from a genuine zero-opportunity observation.

Do not treat `(run_id, decision_seq, public_view_digest)` itself as the state-equivalence key if the sequence changes for an otherwise identical state.

The final rule must preserve all required distinct event records while preventing duplicate state observations from inflating the denominator.

### V2-F05 — MAJOR: Completion, integrity and P2 gate outputs

Specify a complete machine-readable state and exit contract.

Separate at least:

- Execution completion.
- Artifact integrity.
- Input and seed identity validity.
- Trial-selection status.
- Diagnostic validity.
- Mapping-opportunity classification.
- Engineering-timing prerequisite status.
- Overall P2 progression status.

Define all statuses, required evidence, legal transitions and actual process-exit semantics.

Distinguish a valid negative scientific result from invalid, failed, incomplete, missing, or corrupt evidence.

A fully executed and valid trial may still yield NOT_SUPPORTED or INCONCLUSIVE. Neither outcome may be converted into a false PASS.

An exit code of zero must never independently authorize P2 progression.

COMPLETE must not mean mapping opportunity is supported, and mapping opportunity being supported must not imply H/L scientific thresholds pass.

Preserve the existing 2 ms engineering decision-P95 target.

Engineering timing remains outside the current calibration matrix and is NOT_FROZEN. Do not invent timing measurements, silently drop a timing requirement, or claim the full P2 engineering protocol is frozen.

Specify how the unresolved timing prerequisite is represented without mislabelling a calibration-only execution as an overall project pass.

### V2-F06 — MEDIUM: Selection, CI interpretation and result classification

Retain the proposed deterministic A-before-B configuration-selection policy unless the audit establishes a concrete logical defect.

Do not use candidate advantage or mapping-opportunity results to choose the selected configuration.

Explicitly distinguish:

- Registered candidate configurations.
- Fully executed configurations.
- Valid configurations.
- Valid but off-target configurations.
- Eligible configurations.
- Selected configurations.
- Conditions with no eligible configuration.
- Invalid, failed and incomplete trial sets.

Preserve every A/B result, including unselected and off-target configurations.

Explain that selecting a configuration using the same calibration-seed records later used for analysis does not create an independent confirmatory dataset. Any selected-configuration CI must be labelled and interpreted consistently with that selection process.

Do not claim confirmatory inference unless the existing research contract supports it.

No seed deletion, load-bin relabelling, threshold adjustment or result-dependent retry is permitted.

### V2-F07 — MEDIUM: Control, observation-window and numerical semantics

Unify control labels and result schemas.

Specify exact service counts and applicability:

- Main input: 100 services, 50 H and 50 L.
- H_ISOLATED: 50 H services; L metrics explicitly not applicable.
- LOW_COMPETITION: 100 services with the declared control-specific arrival/placement changes.

Define the distinction between:

- Arrival admission window `[0, W)`.
- Last admitted arrival.
- Last service completion.
- Observation end.
- Full-drain makespan.
- Any diagnostic-only window summary.

Do not replace the existing full-drain makespan with `max(W, last_finish)` unless the original metric contract explicitly defines that operation.

Use one exact machine token for control-only N/A metrics.

For the H feasibility lower bound, define the mathematical quantity and its computational verification separately. Specify conservative arithmetic, resource/communication lower-bound assumptions, absolute-deadline conversion, equality handling and rounding rules.

Do not use an arbitrary epsilon. Do not let private true durations or feasibility calculations leak into the scheduler.

Distinguish:

- Proven natural infeasibility when the registered lower-bound criterion is satisfied.
- Failure to establish feasibility.
- A valid control-specific feasibility witness.
- A scheduler correctness failure.

A successful H_ISOLATED control must not be interpreted as proving feasibility under the main arrival process.
