## 三、第二阶段：冻结 P1 实现规格

在编写仿真器前，先建立规格到代码、测试和产物的追踪矩阵。

建议文件：

`docs/P1_implementation_spec.md`

`docs/P1_acceptance_matrix.md`

规格至少必须明确以下内容。

### 3.1 事件驱动仿真模型

实现：

- DAG 任务及前驱关系。
- 任务到达、执行、完成和截止期。
- 异构资源及兼容集合。
- 处理器或资源单元的占用区间。
- 跨资源通信与数据就绪。
- 事件队列及确定性事件推进。
- 每个决策时刻的可观测状态视图。
- 指标计算与可复现的执行轨迹。

实际数据结构必须与模型规格一致，不得仅创建空模块或占位接口就宣称实现完成。

### 3.2 状态可见性与防泄漏

严格区分：

- 真实模拟器内部状态。
- 调度器可以观察的状态。
- 仅用于离线验证的完整事件和真实未来信息。

调度器不得读取：

- 尚未到达的任务。
- 隐藏的未来事件队列。
- 真实未来执行时长或未来完成时间，除非现有协议明确允许该信息。
- 独立验证集和正式评估集的结果。

若模型要求使用估计值，应严格按照既有规格生成或读取估计值，不得用真实未来值替代估计值。

加入负向测试，证明不允许访问的信息无法通过公开状态视图泄漏。

### 3.3 冻结事件顺序

核实 `model_spec.md` 对同时发生事件的规定。

现有交接审计记录的拟定顺序是：

1. 处理同一时刻的完成事件。
2. 处理到达事件。
3. 刷新可观测状态。
4. 评估可行调度决策。

先核对这一顺序是否已经获得正式规格支持。

如果已有明确规定，原样实现并测试。

如果它仍是未冻结的建议，或者与其他文件冲突，不得默默将其提升为正式规则。先在规格差异报告中列出冲突、影响和待裁决问题；不得据此生成 P1 PASS。

相同代码、配置和输入必须产生完全一致的事件顺序、决策轨迹和指标。

## 四、第三阶段：实现 B1–B5 基线

严格沿用现有 `baseline_spec.md` 中的 B1–B5 编号、角色和验收定义，不得擅自改名、增加新基线或改变比较关系。

### B1：EDF + EFT

按照正式规格实现：

- 可调度任务筛选。
- EDF 排序。
- 可行资源枚举。
- EFT 计算与资源选择。
- 明确且确定性的平局裁决。

### B2：H-priority + EDF + EFT

在 B1 基础上实现既定的 H 优先级规则。

验证：

- H 优先级的实际作用范围。
- H 内部排序规则。
- 资源可行性约束。
- 与 B1 的差异。
- 同一输入下的确定性。

不得把 B2 定义成尚未批准的新算法。

### B3：HEFT 在线适配

根据已审查的 HEFT/CPOP 原文和现有基线规格实现。

原文证据包括：

- upward rank 的定义与递推。
- 平均计算与通信代价。
- 基于 rank 的任务排序。
- 插入式 EFT 资源选择。
- 原始算法的假设与复杂度限制。

必须区分原始 HEFT 与本项目的在线适配。不得将未来不可见的任务、真实未来执行时长或其他原文未支持的机制伪装成原始 HEFT 的定义。

### B4：PEFT 在线适配

根据已审查的 PEFT 原文实现：

- OCT 的定义与递推。
- 平均 OCT rank。
- OEFT 资源选择。
- 插入式调度。
- OCT 与处理器可用时间的区别。

必须正确处理 PEFT 原文中 OCT 不包含处理器可用时间、而 EFT 考虑实际部分调度可用性的区别。

不得把自行设计的在线机制写成原论文已有机制。

### B5：H-priority + 原协议指定的映射策略

严格按照现有 B5 定义实现。

核验：

- H 优先级与映射策略的职责分离。
- 候选任务集合。
- 资源兼容性。
- 任务与资源的可行性判断。
- 平局裁决。
- 与 B2、B3、B4 的比较公平性。

不得将 CPOP 自动添加为额外正式基线；只有现行研究契约明确要求时才实现为正式基线。

### B3/B4/B5 规格缺口处理

当前交接审计指出，在线适配的部分细节尚未完整冻结。

先建立决策表，逐项检查：

- ready 集合是否仅含已到达且前驱满足要求的任务。
- 不兼容资源如何处理。
- 忙碌资源的预测何时计算。
- HEFT rank 与 PEFT OCT 何时更新。
- 是否允许等待。
- 平局如何裁决。
- 边界和空候选集合如何处理。
- 任务完成、到达与调度决策之间的关系。

若现有协议可以唯一确定行为，按原协议实现并记录依据。

若某个关键选择会改变算法语义、基线公平性或科学验收标准，且原协议无法唯一确定，**停止受影响基线的实现，不得自行创造规则来制造 PASS**。输出精确的待裁决事项和建议选项；其他不依赖该决策的组件可继续实现和测试。

## 五、第四阶段：资源、通信和执行不变量

实现独立的模型检查与 Trace Validator。

至少覆盖以下不变量。

### DAG 不变量

- DAG 无环。
- 任务 ID 唯一。
- 所有前驱引用有效。
- 前驱完成约束成立。
- 任务到达约束成立。
- 执行时长合法。
- 截止期与完成时间使用一致的单位和边界语义。

### 资源不变量

- 资源 ID 唯一。
- 任务只分配给兼容资源。
- 同一独占资源上的计算区间不得非法重叠。
- 任务不得重复执行。
- 禁止未授权抢占。
- 禁止未授权迁移。
- 已启动区间不得被非法重新规划。

### 通信不变量

- 同资源单元通信按照模型规定处理，若规定为零代价则必须为零。
- 跨单元通信遵守已冻结的延迟和数据量/带宽公式。
- 前驱完成后才能满足对应数据传输条件。
- 计算与传输仅在模型允许的情况下重叠。
- 数据副本位置和重映射必须合法。
- 实际启动时满足前驱、数据、到达和资源条件。

### 独立性要求

Trace Validator 必须独立于仿真引擎内部的合法性判断实现。

不得仅将引擎自己的 `is_valid()` 结果重新打印为 Validator 通过。

使用明确构造的非法轨迹验证 Validator 能够拒绝错误输入。

## 六、第五阶段：确定性与正确性测试

建立手工构造的合成 DAG，不使用科学种子或保留工作负载。

至少包含：

1. 6–8 节点手工 DAG。
2. 多前驱和汇合节点。
3. 不同资源执行时长。
4. 同资源零通信与跨资源通信。
5. 资源忙碌及插入式调度场景。
6. 不兼容任务与资源。
7. 同时到达、同时完成及同刻事件。
8. 截止期恰好相等的边界场景。
9. 所有任务完成后的排空行为。
10. 无可行调度动作时的死锁检测。
11. 空 DAG 或协议允许的最小输入。
12. 非法 DAG、非法资源映射和非法 Trace。

测试至少应包括：

- B1/B2 的手算差异案例。
- HEFT rank 递推与原文定义对照。
- PEFT OCT 递推与原文定义对照。
- EFT 与 OEFT 的资源选择差异案例。
- 兼容集合和忙碌资源测试。
- 平局规则测试。
- B5 H 优先级测试。
- 完整轨迹的独立 Validator 检查。
- 确定性 replay。
- 状态视图防泄漏。
- 不同算法使用相同输入与可比模型参数的公平性检查。

对于每项测试，记录输入、预期结果、实际结果和失败信息。

不能仅以“测试全部通过”代替测试覆盖与证据说明。

## 七、第六阶段：独立 Trace 与指标核验

对每个正确性 fixture：

1. 运行仿真引擎。
2. 保存完整事件轨迹。
3. 使用独立 Trace Validator 检查轨迹。
4. 独立复算任务开始、完成、通信、资源占用和截止期结果。
5. 与引擎输出指标比较。
6. 对同一输入重复运行，验证事件轨迹和指标逐项完全一致。

验证器至少应检查：

- 唯一执行。
- 前驱与数据依赖。
- 到达和完成顺序。
- 资源兼容。
- 资源区间冲突。
- 通信合法性。
- 执行时长。
- 抢占与迁移约束。
- 任务完成计数。
- 截止期判定。

必须保留正例与负例的实际结果。

如果引擎与独立 Validator 不一致，P1 不得通过。
