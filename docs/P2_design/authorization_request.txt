## 3. Treat the five P2 blockers individually

Create a traceable decision table for P2-B1 through P2-B5.

For every blocker, record:
- Exact existing file and line or section.
- What the existing specification actually establishes.
- What remains unspecified.
- Why the missing definition prevents execution.
- Which decisions require human approval.
- Candidate design options supported by existing project constraints.
- Advantages, disadvantages, reproducibility implications, and possible sources of bias.
- The recommended option, if the existing evidence supports a recommendation.
- The exact question that the user must decide.
- The evidence required before the item can be marked resolved.

Do not label an item PASS merely because a draft proposal exists.

### P2-B1: Scientific workload generation

Inspect the workload specification and identify the missing definitions for:
- The three registered workload scenarios.
- The 8-node and 16-node DAG templates.
- Task execution-cost generation across heterogeneous resources.
- Resource compatibility sets.
- Edge data sizes and communication parameters.
- Workload perturbations and their deterministic construction.
- Arrival process, deadline, observation window, and drain behavior.
- H-only feasibility and baseline checks.
- Expected workload identities and artifact structure.

Produce a field-by-field specification gap table.

Do not invent numerical distributions, probabilities, bounds, or feasibility thresholds.

Where no existing source determines a value, provide explicit alternatives for human consideration and mark the value UNRESOLVED.

### P2-B2: Finite calibration trial matrix

The registered 3×3×2 main-condition structure must not be treated as a complete experiment matrix by itself.

Identify the exact missing definitions for:
- Parameter axes and legal values.
- The full finite list of trials and configurations.
- Which methods are included in each trial.
- The role of B2 as the focal reference.
- The permitted baseline subset and the justification for its selection.
- Trial ordering and run budget.
- Selection criteria and deterministic tie handling.
- Treatment of failed, invalid, infeasible, or incomplete runs.
- The mapping from calibration seeds to workloads and conditions.

Do not select a method subset or parameter values without documented support.

Provide a machine-readable DRAFT matrix only if every unresolved field is explicitly marked as unresolved and the draft cannot be mistaken for an executable or approved matrix.

### P2-B3: Mapping-opportunity criterion

Read `docs/statistical_protocol.md` and all existing definitions of mapping opportunity.

Identify what is required to turn the registered concept into an executable criterion:
- The observable quantity.
- The comparison or counterfactual.
- The unit of analysis.
- The aggregation across seeds, scenarios, and conditions.
- The stability criterion.
- The treatment of uncertainty.
- The definition of infeasible or invalid observations.
- The decision rule for SUPPORTED, NOT_SUPPORTED, and INCONCLUSIVE.
- The required output evidence and audit trail.

Present explicit alternative formulations only where they can be justified by existing project requirements.

Do not invent a new threshold or select the criterion after examining scientific outcomes.

Do not silently equate mapping opportunity with H improvement, L compliance, or the eventual success of a candidate scheduler.

No mapping-opportunity result may be computed in this task.

### P2-B4: Scientific execution entry point

Inspect the current pipeline and existing recovery infrastructure.

Prepare a design for the future P2 runner covering:
- Explicit input and configuration identities.
- Registered calibration seed enforcement.
- Deterministic workload materialization.
- Run IDs and source/configuration/input hashes.
- Invocation records, actual exit codes, and failure preservation.
- Trace validation and metric computation.
- Incomplete-run detection and restart behavior.
- Idempotency and duplicate-output detection.
- Fail-closed behavior for missing or corrupted artifacts.
- A machine-readable P2 gate decision.

Do not implement the runner or call the P2 entry point in this task.

### P2-B5: Scientific artifact schema

Distinguish scientific run artifacts from P1 hand-authored correctness fixtures.

Prepare a proposed schema for:
- Scientific workload identity and provenance.
- Actual seed identity and partition.
- Scenario, condition, method, and configuration identity.
- Source, model, configuration, and input hashes.
- Simulator invocation and exit status.
- Trace validation outcome.
- Metrics and their derivation.
- Run completeness and error status.
- Links to raw outputs and logs.

A P1 fixture must never become a scientific sample through relabeling.

Any new schema must preserve compatibility with the existing frozen protocol and existing P0/P1 artifact identities.

Do not claim schema correctness merely because a JSON document parses.
